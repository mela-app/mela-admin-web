# Live chat & likes

**Location**: `apps/backend/src/chat`, `apps/backend/src/common/rate-limit`, `apps/backend/src/common/throttle`, `apps/mobile/lib/features/chat`
**Plan reference**: plan §6.3, §6.9, §6.13, §6.14; task-breakdown Phase 2 & 4
**Depends on**: `common/prisma`, `common/redis`, `common/presence` (like totals live there, next to viewer counts), `streams` (history checks the stream is live), `auth` (the realtime gateway authenticates the socket; the REST history endpoint has its own `JwtAuthGuard`), `moderators` (delete/pin capability checks), `common/permissions` (`hasChannelCapability`)
**Depended on by**: `realtime` (the gateway hosts `chat:send`/`like:send`/`chat:delete` and relays `chat_message.deleted`/`pinned`/`unpinned` - no second Socket.IO server, see plan §4.1)

## What it does

Chat and likes ride the existing realtime gateway and its `stream:{id}` room - there is no separate chat service or socket namespace.

**Chat send** (`chat:send` on the gateway, anyone in the room including the host, plan §5): `ChatService.send()` runs the cheapest checks first -
1. `cleanChatText()` (`chat-text.ts`): Unicode-normalizes the text, strips control characters and the bidi-override characters used in "Trojan Source" attacks, collapses whitespace runs, caps any repeated character (emoji/character floods) at 5 in a row, then trims. Empty -> `MESSAGE_EMPTY`; over `CHAT_MAX_LENGTH` (200 code points, so a multi-byte emoji counts once) -> `MESSAGE_TOO_LONG`.
2. A resend check: the app sends a per-message `clientId`; if the same one was already persisted in the last `RESEND_WINDOW_SECONDS` (120s), the earlier message is returned again (`resent: true`) instead of creating a duplicate - covers a reply lost after the server actually saved it.
   - Then the room chat mute (plan §6.7, Phase 7): a sender muted in this live (`RoomChatMutesService.findActive()`, docs/features/moderation.md) -> `CHAT_MUTED`, with `retryAfterMs` until a timed mute lifts (none: until the live ends). After the resend check on purpose, so a message that went through before the mute still gets its answer.
3. `BannedPhrasesService.match()` (plan §6.3): a `REJECT`-severity phrase anywhere in the text -> `MESSAGE_BLOCKED`, checked before the rate limit so a blocked message never spends a token.
4. `RateLimitService.take()`: a Redis-backed token bucket, atomic via a Lua script (`EVAL`) so concurrent requests can't race past the limit - `capacity` tokens at once, refilling one every `refillMs`. Chat's bucket (`CHAT_RATE_LIMIT`) is 3 messages at once, then one every 1.5s, keyed per `streamId`+`userId`. Over the limit -> `RATE_LIMITED` with `retryAfterMs`.
5. `hasDisallowedLink()` (`link-policy.ts`, plan §6.3): any URL whose domain isn't one of `CHAT_LINK_DOMAINS` (or a subdomain of one) -> `LINK_NOT_ALLOWED`. A pure/sync regex check, no DB access - runs after the rate limit since it's marginally more expensive than a Set lookup but still far cheaper than a query.
6. `BannedPhrasesService.mask()`: any `MASK`-severity phrase left in the (already-not-rejected) text is blanked out before persisting - the message still sends, just with the phrase redacted.
7. Persists via Prisma (`chat_messages`), then the gateway broadcasts `chat:new` to everyone else in the room (`socket.to(room).emit(...)`) - the sender already has the message in their own `chat:send` acknowledgement.

A rejected send comes back as `{ok: false, error, retryAfterMs?}` on the same acknowledgement (no separate `chat:rejected` event) - the mobile client reads the ack directly (`RealtimeRejected`, thrown by `LiveRoom.sendChat`/`sendLikes` from a `{ok:false}` response).

**The host's photos** (client request, 2026-09-30): the host can post a photo into their live's chat, with an optional caption; nobody else can. Two steps, so the image never passes through the API:
1. `POST /v1/streams/:streamId/chat/image-upload-url {contentType}` (`ChatController`, `image/jpeg` or `image/png`, 20 per minute; 404 when the live is over, 403 for anyone but its host) returns `{uploadUrl, publicUrl, imageKey}` - a 5-minute presigned PUT for a fresh key `chat-images/<streamId>/<uuid>.<jpg|png>` (`chat-images.ts`, docs/features/storage.md). The app uploads the bytes there directly.
2. `chat:send {streamId, clientId, imageKey, text?}` - `text` is the caption, and may be left out. `ChatService.send()` then also requires the sender to be the live's host (`NOT_ALLOWED` otherwise) and the key to be one handed out for this live (`isChatImageKey` - another live's photo, another object in the bucket or any other URL is `IMAGE_INVALID`), and stores the object's public URL (`StorageProvider.publicUrl`) in `chat_messages.imageUrl` (migration `20260930130000_chat_images_recording_permissions`). The caption goes through every usual step (cleaning, phrase filter, link policy); an empty one is fine for a photo, an over-long one isn't. Rate limit and resend handling are the same as for text.

Every message view (`chat:new`, the send answer, history) carries `imageUrl` (null for text). Where only a line of text fits - the pinned banner, from `pin()` and `StreamsService`'s join snapshot - a photo reads "📷 Photo" or "📷 <caption>" (`chatPreviewText`). Deleting a photo message works like any other (the object stays in storage). The admin console's chat log shows the thumbnail; the share page's web player shows photos in its chat too.

**Banned phrases & link policy** (`apps/backend/src/chat/banned-phrases.service.ts`, `link-policy.ts`, plan §6.3): `BannedPhrase` rows (`phrase`, `severity` `REJECT`/`MASK`) are a real table, not static config, so they can be updated without a deploy (the admin console's banned-phrase screen writes to the same table, and each change clears this cache at once through the `banned_phrase.*` events). `BannedPhrasesService` caches the list in-process for 30s (`phrases()`) rather than querying on every single chat message, and compiles each phrase into a fuzzy regex (`toFuzzyPattern`) tolerant of leetspeak substitutions and inserted separators (e.g. "s.p.a.m", "sp4m") so simple obfuscation doesn't slip through. `hasDisallowedLink()` is unrelated to the phrase list - an allowlist of the platform's own domains from the `CHAT_LINK_DOMAINS` environment variable (comma-separated; empty means no links at all), read once by `ChatService` at start-up and checked via a URL-matching regex.

**Chat delete** (`chat:delete {streamId, messageId}` on the gateway): chat is moderated, not edited by its senders (client feedback, 2026-09-29) - `ChatService.delete()` is the **host's** call (any message), or a delegated moderator's holding `DELETE_MESSAGES` (`canUseCapability()`, which checks `PermissionsService.isHost()` first and only fetches the requester's `ModeratorGrant` via `ModeratorsService.findActiveGrant()` when they aren't) - never a plain viewer's, not even for their own message. Anyone else gets `NOT_ALLOWED`, decided before the message is looked at, so it never says whether one exists. A moderator reads the message's sender first: another moderator's or the host's message is `NOT_ALLOWED` too (`PermissionsService.moderationTargetRefusal`, docs/features/moderators.md) - their own is fine. It soft-deletes (`moderationStatus -> DELETED`, the row stays for audit) with a conditional `updateMany`; an already-deleted or unknown message is `NOT_FOUND`. A successful delete emits the `chat_message.deleted` domain event (`{streamId, messageId, actorId}` - `actorId` is whoever actually deleted it, for the audit trail, plan §6.9), and `RealtimeGateway.handleChatMessageDeleted` - not the socket handler itself - is what broadcasts `chat:deleted {streamId, messageId}` to **everyone** in the room, the deleter's own other devices included. Routing the broadcast off the domain event (the same "decoupled from the gateway" pattern as `StreamEnded`/`StreamLayoutChanged`, see docs/features/events.md) means any future non-socket path that can delete a message (an admin endpoint, say) gets the same realtime broadcast for free, instead of needing its own copy of the emit.

**Pinned message** (`POST/DELETE /v1/streams/:streamId/pin`, `StreamPinController` - deliberately inside `ChatModule`, not `StreamsModule`, since `ChatModule` already imports `StreamsModule` and the reverse import would cycle): host or a moderator holding `PIN_MESSAGES` pins one existing, visible message to the top of chat (`ChatService.pin()`), or unpins whatever's currently pinned (`ChatService.unpin()`) - one pin per live, stored as `Stream.pinnedMessageId`. Both emit `chat_message.pinned`/`chat_message.unpinned` (`{streamId, messageId?, actorId}` - pin also carries `text`/`senderName`, a small snapshot so a client that doesn't already have that message loaded locally can still render the banner without a dedicated fetch), relayed by the gateway to the room as `chat:pinned`/`chat:unpinned` - the same decoupled-broadcast pattern as delete. `ChatPinResult` (`{ok:true} | {ok:false, error:'NOT_FOUND'|'NOT_ALLOWED'}`) maps to 404/403 in the controller. `StreamsService.join()` separately returns a `pinnedMessage` snapshot (the same `{id, text, senderName}` shape, via a small direct Prisma read - it can't call `ChatService` itself, same circular-import reason) so a viewer joining after the pin happened sees it immediately, not just from the next live `chat:pinned`.


**Chat history** (`GET /v1/streams/:streamId/chat`, `ChatController`, JWT-guarded, cursor-paginated via `ChatHistoryQueryDto`): no cursor returns the latest `limit` (default 50, max 100) messages; `before` (a message id) pages older messages for scrolling up; `after` returns only what arrived since that id, for a reconnect. Messages are queried newest-first (to pick the right window off the id, which is time-ordered UUIDv7) and handed back oldest-first. `hasEarlier` tells the caller whether the window was cut short - either older history exists (`before`/no cursor) or, with `after`, more arrived than fit in one page (a gap the client should treat as "start over from the latest"). Only `VISIBLE` messages are returned - a deleted message simply stops appearing in any history fetched after it's gone.

**Likes** (`like:send {count}` on the gateway, viewers only - a host liking their own live is rejected with `NOT_ALLOWED`): `LikesService.add()` rate-limits per `streamId`+`userId` (`LIKE_RATE_LIMIT`: 3 batches at once, then one a second) then calls `LivePresenceService.addLikes()`, a Redis `INCRBY` (`likes:{streamId}`, alongside the other per-stream presence keys). The new total is never sent straight back to the room - `KeyedThrottle` schedules a `likes_update {streamId, total}` broadcast at most once a second (`LIKES_THROTTLE_MS`), leading **and** trailing: the first tap after a quiet room broadcasts at once, and every tap inside the window collapses into exactly one broadcast when it ends, so a burst of likes can't flood the room and the final count is never dropped. `RealtimeGateway.flushLikes()` re-reads the Redis total (rather than trusting the value from any one request) before emitting. The viewer-count broadcast uses the same `KeyedThrottle` class (`VIEWER_COUNT_THROTTLE_MS`, 2s) - the throttling logic is written once, not copied per feature.

`streams.likeCount` (migration `20260926100000_add_chat_messages_and_like_count`) is 0 until the stream ends: `StreamsService`'s shared `endStream()` reads `LivePresenceService.likeCount()` alongside `peakViewerCount()` and persists both in the same update that marks the stream `ENDED`. A live's `GET /v1/streams/:id` and the join/go-live responses also expose the *current* like count while it's running (Redis) so joining mid-live shows the right number, falling back to the persisted column once it's over.

**Rate limiting** (`common/rate-limit/rate-limit.service.ts`) is a generic per-key token bucket (`RateLimitService.take(key, {capacity, refillMs})`), reused by both chat and likes with their own keys/limits - not two separate implementations.

**In the admin console** (docs/features/admin.md): a live's **Chat log** tab (`GET /v1/admin/streams/:id/chat`, newest first, refreshing while the live runs), and the **Live chat** page, which arranges chat like private messages - a day at a time, by host, each host's chat that day under a heading per live (`GET /v1/admin/chat/hosts[/:hostId]`). Both show every moderation status, with search, a status filter, delete and suspend. A delete there - one message, or many picked at once (`POST /v1/admin/chat/messages/delete`) - **erases** it: `ChatService.eraseAsAdmin` deletes the row and its photo file, unpins it if pinned, and sends the room the same `chat:deleted`, carrying what the message said in `chat_message.deleted`'s `erased` for the audit entry (the row can't be read afterwards). A host's or moderator's delete stays a `DELETED` status, kept for review.

## Mobile (`apps/mobile/lib/features/chat`, wired into both `live_stream/viewer_screen.dart` and `live_stream/go_live_screen.dart`)

`ChatRepository` (`data/`) wraps the history REST call; `LiveChatController` and `LiveLikesController` (`presentation/`, both `ChangeNotifier`) own the client-side state and listen to the same `LiveRoom` every other realtime feature uses (`live_stream/live_room.dart`) - nothing here talks to Socket.IO directly.

**Chat**: `LiveChatController` keeps posted messages plus this device's own unconfirmed ones (`OutgoingLine`, shown immediately, retried up to 3 times on `RATE_LIMITED` using the server's `retryAfterMs`, marked failed - tap to retry - once attempts run out) capped at `maxMessages` (300, oldest trimmed; scrolling up reloads them from history). On every room (re)join it calls `history(after: <last message id>)` - the first join has no cursor and gets the latest page; a reconnect only fetches what's new, and a gap (`hasEarlier` on an `after` query) clears local state and starts over from the latest rather than showing a hole. `ChatOverlay` shows the last messages newest-at-the-bottom with a top edge that fades into the video (`ShaderMask`, only once the list actually fills the space), holds back messages that arrived while the reader scrolled up (a "New messages" pill, tap to jump back down), and shows a skeleton (`_ChatSkeleton`) until the first page loads. Each bubble leads with the sender's avatar (`core/widgets/user_avatar.dart` - their photo, or an initial on a themed circle otherwise, TikTok-style); an unconfirmed `OutgoingLine` shows a plain "You" placeholder since it doesn't carry the sender's own avatar URL. `ChatComposer` is a "Say something…" pill capped at 200 characters (`ChatComposer.maxLength`, matching `CHAT_MAX_LENGTH`) that stays open and gives a `HapticFeedback.selectionClick()` after a send. A plain viewer can send chat but is never issued a publisher video/audio token (plan §5) - chat and being on-stage are unrelated.

**Muted in this live** (plan §6.7, Phase 7): `LiveChatController.isMuted`/`mutedUntil` follow `RoomSynced.chatMuted` (every rejoin) and `SelfChatMuteChanged` (`chat:muted`/`chat:unmuted`); a timed mute unlocks itself when it runs out (a local timer - the server announces nothing then). While muted, `send()` refuses and `ChatComposer.lockedMessage` replaces the field with the reason (`chatMutedNotice`: "for the rest of this live" / "until 6:30 PM"), keeping anything already typed. A `CHAT_MUTED` rejection locks it straight away too (the notice may still be on its way), and each rejection code has its own failure text (`_failureText`). The viewer screen shows a snack bar when a mute starts or lifts.

**Hidden senders** (plan §6.4, §6.7): `LiveChatController.hiddenSenderIds` - the people this account muted in chat or blocked, from `chatFilterProvider` (`features/chat/application/chat_filter.dart`, loaded on sign-in and again as each live opens) - drops their messages from `lines`, including ones already shown; clearing it brings them back. The filter is client-side by design: the hidden person is unaffected and isn't told (docs/features/social.md).

**Photos** (`chat_photo.dart`): on the host's go-live screen, `ChatComposer.onPickPhoto` puts a photo button where Send sits while nothing's typed. It opens the gallery (`image_picker`, scaled to 1080 px at quality 75 - every viewer downloads it; the camera itself is busy with the live), then `showChatPhotoPreview` shows the photo with an optional caption before it goes. `LiveChatController.sendPhoto()` shows it at once as an `OutgoingLine` carrying the picked bytes (`OutgoingPhoto`), uploads it (`ChatRepository.uploadImage`), then sends it like any message; a retry after a failed upload uploads again, one after a failed send reuses the uploaded key. In a bubble, `ChatPhoto` shows the photo small (decoded at its display size), and a tap opens it full screen (`showChatPhoto`, pinch to zoom). With Data Saver on, a viewer's photos wait behind "Tap to load photo" (`ChatOverlay.holdPhotos`).

**Likes**: `LiveLikesController` counts every tap immediately (`total` = server-confirmed + this device's own queued/in-flight taps, so the UI never goes backwards) and batches taps into `like:send {count}` calls - at most one batch in flight at a time, at most `maxBatch` (30, matching the server's `MAX_LIKES_PER_BATCH`) per batch, the first tap after a quiet spell flushed after only `_firstBatchDelay` (300ms) so a quick burst still reads as responsive, subsequent batches at most once a second (`batchInterval`). A `RATE_LIMITED` rejection re-queues that batch's taps rather than dropping them. **Viewers like by tapping the video** - each tap one like, TikTok-style (`LiveStage.onVideoTap`; a tap that only brings Minimal's controls back, or one that puts the keyboard away, doesn't count). There's no like button (client feedback, 2026-09-29): the hearts are the feedback, and screen readers get the same action on the video (a synthesized tap counts from the middle of it). Hearts float for **everyone in the room**: the viewer's own taps from the tap point, with a `HapticFeedback.lightImpact()`; other people's likes from near the bottom-right corner as each `likes_update` total arrives (`LiveLikesController.othersLiked`, at most once a second per live - `FloatingHeartsController.burst()` with no origin, `FloatingHearts.restingInset`); on the host's screen every rise in the total does the same, after the room's first sync so a late join doesn't float them all at once. The host's like total is a `LikeCountBadge` in their top bar. The effects layer ends above the bottom panel, so hearts start clear of the controls. With reduce-motion on, no hearts.

**@mentions**: typing `@` in `ChatComposer` lists who can be named - the host first, then whoever is watching, never yourself or anyone blocked either way (`GET /v1/streams/:id/mention-suggestions?q=&limit=`, `StreamsService.mentionSuggestions`, a prefix match on username or display name) - in a list floating just above the field (an `OverlayPortal` following the composer, inside a `TextFieldTapRegion` so picking keeps the keyboard up; nothing on the stage moves). Lookups wait 150 ms after the last keystroke, and a longer name narrows the last answer on the spot while the next one is on its way; a failed lookup just shows nothing. Picking completes `@username ` (`insertMention` in `domain/chat_mentions.dart`, which also finds the name being typed - `mentionAt` - and ignores an email address). Messages carry `mentions: [{id, username}]` - the server resolves every `@username` in the text to an account at send time and in history (`chat/mentions.ts`: at most `MAX_MENTIONS_PER_MESSAGE` = 10, case-insensitive with an exact match winning, one lookup per history page, none when nobody is mentioned; no schema change), so a typed name that isn't anyone stays plain text. A mention shows bold in `AppColors.primaryLight`, and a message that mentions this viewer stands out (a brand-tinted bubble with a border).

**Tapping a person in chat** - a sender's name or picture, or a mention - calls `ChatOverlay.onPersonTap`; both live screens open that person's profile card (`showProfileCard`, docs/features/social.md), which shows only what their profile visibility lets this viewer see, with a "..." menu of everything this user's role allows doing to them (ban, mute in chat, the stage, moderator, block - docs/features/moderators.md). The tappable name and mentions are `TapGestureRecognizer`s owned by `_MessageText` (made once per message text, so a rebuild mid-tap doesn't drop it); screen readers get the same action on the bubble, with the long-press action sheet alongside.

**Replying** (client feedback, 2026-09-29): a tap anywhere else on someone's message (`ChatOverlay.onMessageTap` - never on your own) starts a reply: `ChatComposerController.replyTo(username)` puts `@username ` in front of the draft and brings the keyboard up. What was already typed stays; a draft that already opens with a name switches to the new one (`replyDraft` in `domain/chat_mentions.dart`). The server resolves that `@username` like any other mention, so the person replied to sees their message highlighted. Messages carry the sender's `username` for this (`ChatMessageView.sender`, `ChatMessage.senderUsername`). The name and mention spans win their own taps (they're deeper in the gesture arena), so a tap on the name still opens the profile. Screen readers: double-tap replies, and a custom action opens the profile.

**Clear screen and chat toggle**: a viewer's controls - chat included - clear after a minute without a touch, and any touch brings them back (`LiveStage.idleHideAfter`, docs/features/streams.md); a dedicated button in the bottom panel (`Icons.speaker_notes_off_rounded`) hides only chat. The host has the same chat toggle next to their own composer.

**Message action sheet** (long-press a bubble, `features/moderation/presentation/message_action_sheet.dart` - plan §6.9; trimmed to the message itself by client feedback, 2026-09-29): the sheet shows only what this device is actually allowed to do, as `ModerationPolicy` (`features/moderation/domain/moderation_policy.dart` - the server's rules, docs/features/moderators.md) says - **Pin/Unpin** for the host or a moderator holding `PIN_MESSAGES`, **Hide messages from …** (anyone, on anyone else's message except the host's - personal chat mute, with Undo), and **Delete** for the host (any message) or a moderator holding `DELETE_MESSAGES` (not the host's, nor another moderator's). What's about the *person* - View profile, Mute in chat, Ban - moved to their profile card's "..." menu (tap their name), so there's one place for it. With nothing to offer (a viewer's own message, or the host's for a viewer) there's no sheet at all. Delete keeps its own confirm dialog (`core/widgets/confirm_dialog.dart`, destructive) and the same optimistic-remove-then-restore-on-refusal behavior as before (`LiveChatController.delete()`); pin/unpin are plain calls to `LiveStreamRepository` - their effect on OTHER devices arrives back through `chat:pinned`/`unpinned`, not a direct response to this action, so a moderator's own screen doesn't do anything special on success beyond a failure snackbar. Everyone's copy of a delete disappears together via `chat:deleted` -> `ChatMessageDeleted` (`live_room.dart`) -> `LiveChatController._onRoomEvent`, including on the deleter's own other devices; a delete that arrives for a message already gone locally (e.g. the deleter's own echo) is a no-op.

**Moderator badge**: a small green "MOD" tag (`features/moderation/presentation/moderator_badge.dart`, distinct from the host's gradient "HOST" tag) shows next to **every** moderator's name - in chat, the viewer list and the guest manager. Everyone in a live knows who moderates it (client feedback, 2026-09-29: moderators can't act on each other, and the badge is how anyone tells them apart): `stream:join` answers `moderatorIds`, and `stream:moderators` updates the room as the host appoints or removes one (docs/features/realtime.md). What each moderator may do stays private to them.

**Host chat** (`go_live_screen.dart`): the host gets the same `ChatOverlay`/`ChatComposer`/`LiveChatController` as a viewer, in the live controls' bottom panel, with `selfIsHost: true` - they can read and send chat (mentions included), reply by tapping a message, open anyone's card, and delete/pin/ban through the same action sheet; they don't like their own live (the server rejects it, see **Likes** above) - they see the hearts. Chat only exists once actually live (`_isPublishing`), not during the pre-live camera preview.

**Host live controls** (`go_live_screen.dart`, `_buildLiveControls()`): mic on/off and camera on/off buttons call `HostVideoSession.setMedia({camera, microphone})` directly - independent of Pause (which turns both off and additionally puts every viewer on a dedicated "paused" screen via `LiveRoom.setPaused`). Viewers learn the host's camera/mic state from the video vendor's own mute callbacks (Agora `onUserMuteVideo`/`onUserMuteAudio`, LiveKit's track-mute events), surfaced as `ViewerVideoSession.isHostCameraOn`/`isHostMicOn` (`video/video_session.dart`) - there is no separate `host_media_state`-style realtime event, since the video channel already carries it. The buttons are hidden while paused (both are already off then) and disabled mid-toggle; resuming from Pause always turns both back on.

**Mentioning anyone in the live** (client feedback, 2026-10): typing `@` already suggests everyone watching, not only who chatted (`GET /streams/:id/mention-suggestions` reads the viewers from presence). Every profile card opened in a live - from the viewer list, a chat name, a guest tile or the host's pill - also has a **Mention** button (`@`): it closes the card (and the viewer list) and puts `@username ` in the chat box with the keyboard up (`LiveMemberScope.mention` → `ChatComposerController.replyTo`). Not on one's own card, nor someone blocked.

## How to add to this feature

- **A new banned-phrase severity or matching rule**: `BannedPhrasesService.toFuzzyPattern()`/`match()`/`mask()` are the only places phrase matching happens - a new `BannedPhraseSeverity` enum value needs a Prisma migration plus a branch in `match()`'s REJECT-first sort and `mask()`'s masking logic.
- **A new allowed link domain**: add it to `CHAT_LINK_DOMAINS` in the backend's environment and restart - no migration or code change (it's deliberately not a DB table; if it needs to be admin-editable later, promote it to one, mirroring `BannedPhrase`).
- **A new moderator capability gating some other chat action**: add the enum value (`ModeratorCapability`, Prisma migration), then check it the same way `delete()`/`pin()`/`unpin()` do via `canUseCapability()`/`hasChannelCapability()` - no new authorization pattern needed.
- **A new rate limit**: reuse `RateLimitService.take()` with a new key/`RateLimit`, the way `CHAT_RATE_LIMIT`/`LIKE_RATE_LIMIT` do - don't hand-roll another token bucket.
- **A new throttled broadcast**: reuse `KeyedThrottle`, the way likes and the viewer count do.

## How to modify this feature

- Message length, flood cap, or the rate limits are single constants (`CHAT_MAX_LENGTH` in `chat-text.ts`; `CHAT_RATE_LIMIT`/`LIKE_RATE_LIMIT`/`MAX_LIKES_PER_BATCH` in their services/DTOs) - change them there, not per call site.
- Who can chat/like is enforced in the gateway handlers (`onChatSend`/`onLikeSend`), not `ChatService`/`LikesService` - e.g. the host-can't-like-their-own-live rule is a room/socket check (`socket.data.hostingStreamId`), so a future moderation mute would likely gate the same way. Who can **delete or pin**, though, *is* in the service (`ChatService.delete()`/`pin()`/`unpin()`, via `canUseCapability()`) since it needs the message's/stream's ownership, not just the socket's own claims.
- The banned-phrase cache TTL (30s, `BannedPhrasesService`) trades freshness (how quickly a newly-added phrase takes effect) for query load - one constant to change if that trade-off needs to shift.

## How to remove this feature

Remove `ChatModule` from `RealtimeModule`'s imports and `AppModule`'s imports, delete the `chat:send`/`like:send`/`chat:delete` handlers (and `flushLikes`/`likeTotals`, and the `chat_message.deleted`/`pinned`/`unpinned` `@OnEvent` handlers) from `RealtimeGateway`, and drop the `ChatOverlay`/`ChatComposer`/`FloatingHearts` wiring (and `onVideoTap`'s like) from `viewer_screen.dart` and the `ChatOverlay`/`ChatComposer` wiring from `go_live_screen.dart`. `streams.likeCount`, `chat_messages`, `banned_phrases`, and `Stream.pinnedMessageId` are additive - safe to leave until a migration removes them. Removing just the pin feature on its own: delete `StreamPinController`/`pin-message.dto.ts`, the `pin()`/`unpin()` methods and `ChatPinResult` type from `ChatService`, and the `ChatMessagePinned`/`Unpinned` domain events + gateway handlers.

## Tests

Backend: `chat.service.spec.ts` (clean/reject/resend/rate-limit/history windowing; banned-phrase REJECT/MASK; link-policy rejection; delete: self, host, a moderator with/without `DELETE_MESSAGES`, refused, not-live; pin/unpin: allowed, refused, not-found), `chat-text.spec.ts` (cleaning rules), `likes.service.spec.ts` (rate-limit, Redis increment), `rate-limit.service.spec.ts` (token bucket timing), `keyed-throttle.spec.ts` (leading+trailing coalescing), plus `realtime.gateway.spec.ts` (the `chat:delete` handler no longer broadcasts directly - it hands off to `handleChatMessageDeleted`, tested separately; `handleChatMessagePinned`/`Unpinned`) and `streams.service.spec.ts` for end-of-stream `likeCount` persistence. End-to-end: `apps/backend/scripts/smoke-test-realtime.js` exercises chat send/relay/rate-limit/pagination/resend-dedup and likes batching/rate-limit against a live dev server.

Mobile: `live_chat_controller_test.dart` (first-join load, reconnect resync, the gap-recovery start-over, live arrivals, send/retry/give-up/manual-retry, `loadEarlier`, the `maxMessages` trim, delete with rollback-on-refusal, a remote `chat:deleted`; "mute suite": a join-reported mute and its lift, a timed mute running out on fake time, an already-expired mute, a `CHAT_MUTED` rejection, hidden senders), `chat_composer_test.dart` (the locked composer keeps typed text), `chat_filter_test.dart` (load, optimistic mute with rollback, a slow refresh can't undo a newer change, blocks) and `live_likes_controller_test.dart` (the synced starting total, batching/coalescing, the in-flight-batch queue, `maxBatch` capping, a rate-limited batch being re-queued, `othersLiked`, flushing on dispose) - both against a `FakeTransport`/fake `ChatRepository`, no real socket or HTTP. `api_client_test.dart` covers `currentUserId()` (decoded from the stored token, null when signed out). `live_room_test.dart`'s "moderation" group covers the `chat:pinned`/`unpinned` and `moderator:*` event routing that feeds the pinned banner, badge, and action sheet - see docs/features/streams.md's Tests section for the exact cases (including a real routing bug it caught). `message_action_sheet.dart`/`moderator_badge.dart`/`moderators_screen.dart`/`viewer_list_sheet.dart` themselves have no dedicated widget tests yet - their logic is either a thin pass-through to already-tested repositories, or (the capability/pin-state gating in the action sheet) plain conditionals exercised manually; a widget-test pass over these screens is a reasonable next addition, not done in this round.

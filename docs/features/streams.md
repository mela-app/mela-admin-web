# Streams (go live / watch)

**Location**: `apps/backend/src/streams`
**Plan reference**: plan §6.1, §6.4, §6.9, §6.13; task-breakdown Phase 1 & 4
**Depends on**: `common/prisma`, `common/permissions`, `common/video-provider`, `common/events`, `auth` (for `JwtAuthGuard`), `social` (the `feed=following` filter, blocked-host exclusion, and `isFollowingHost` on join - see docs/features/social.md), `moderators` (capability checks for bans and its own grant/list/update/revoke logic - see docs/features/moderators.md), `room-bans` (the ban/unban store and the `join()` enforcement check)
**Depended on by**: `realtime` (listens for `stream.ended`, `stream.layout_changed`, and `room_ban.created`); `guests` and the admin console (`lock`, `unlock`, `lockLiveStreamsOfHost`) read/write the `streams` table; notifications consume `stream.started`

## What it does

`POST /v1/streams` (go live), `GET /v1/streams` (discovery), `GET /v1/streams/:id` (one live, running or over), `GET /v1/streams/config` (which video provider new lives use, plus what the mobile go-live screen's pre-publish camera preview needs - no stream/token side effects), `POST /v1/streams/:id/join` (mint an audience token; also reports `isFollowingHost` (so the viewer screen's host pill knows whether to show Follow), `selfCapabilities` (this viewer's own moderator capabilities for this **stream** - `[]` if none, plan §6.9, so the app knows what to show from the moment it joins, not just from the next `moderator:updated` push), and `pinnedMessage` (a `{id, text, senderName}` snapshot of the currently pinned message, or `null` - plan §6.13); 403s if the caller is room-banned), `POST /v1/streams/:id/watch` (the share page's web player: optional sign-in, 20 per minute per IP - an audience token for an anonymous `web-<uuid>` viewer plus a watch ticket for its watch-only socket, and the stream, `isFollowingHost`, `pinnedMessage`, `activeGuests`, `hostAgoraUid`, `serverTime`; 404 once the live is over, 403 for a signed-in viewer who's room-banned - see docs/features/share.md), `POST /v1/streams/:id/end` (host-only), `GET /v1/streams/:id/viewers` (paginated viewer list, plan §6.13), `POST/DELETE /v1/streams/:id/bans/:userId` (room ban/unban, plan §6.4), `GET/POST /v1/streams/:id/moderators` and `PATCH/DELETE /v1/streams/:id/moderators/:userId` (delegated moderators, scoped to this one stream - plan §6.9, see docs/features/moderators.md). The stream's own id doubles as the seed for its channel/room name (`channelName`, via `createChannelName`), generated client-side-of-the-DB with `crypto.randomUUID()` so the row can be inserted once, fully formed - no placeholder-then-update step.

**Discovery** (`GET /v1/streams?category=&feed=&page=&limit=`, public unless `feed=following`): `LIVE` streams only - ended ones are never listed ("no history once a live ends"); `status=live` is still accepted for older apps. Ranked by current viewer count (unique users, from `common/presence` in one Redis pipeline), then newest first, and paginated after ranking, so page 2 continues page 1's order; ranking is done over at most `MAX_RANKED_LIVES` (500) lives. `category` matches case-insensitively. `feed=following` narrows the list to streams whose host this caller follows - it requires a signed-in caller (`OptionalJwtAuthGuard` on the route; the *service* throws `UnauthorizedException` for this one query shape specifically, not the whole endpoint) - see docs/features/social.md. For a signed-in caller, streams whose host they've blocked (either way) are excluded too (plan §6.4) - `listLive()` merges the `feed=following` `in` filter and the block `notIn` filter into one `hostId` object, since spreading two separate `{hostId: ...}` filters into the same `where` would let the second silently overwrite the first (the same bug already fixed once in `SocialService.search()` - see docs/features/social.md). Response: `{items: [{id, title, category, status, startedAt, endedAt, host: {id, username, displayName, avatarUrl}, viewerCount, paused}], total, page, limit}` - a paused live keeps its rank. If Redis is down, the list still loads with zero counts.

**One live** (`GET /v1/streams/:id`, public; the id must be a UUID): `{id, title, category, status, layout, startedAt, endedAt, endedReason, peakViewerCount, host, viewerCount, paused, serverTime}` - what a viewer opening a stale card or a shared link needs, and how the apps learn why a live ended. Go-live and join responses also carry `stream.host` and `serverTime`, which the apps' live timer is synced to.

**Why a live ended** (`streams.endedReason`, the `StreamEndReason` enum, also sent in `stream_ended`): `HOST_ENDED` (the host tapped End), `HOST_DISCONNECTED` (the sweeper: no heartbeat for 90 s - docs/features/realtime.md), `REPLACED` (the host went live again). Ending is conditional (`updateMany … where status = LIVE`), so when the host, the sweeper and a new go-live race, exactly one of them ends it, emits the event once and persists `peakViewerCount`.

**Video provider per stream**: go-live puts the live on the active vendor (`VIDEO_PROVIDER`) and stores it in `streams.videoProvider`; join and end always use that stored vendor, so switching `VIDEO_PROVIDER` never strands a running live. Go-live opens the media channel *before* inserting the row (on LiveKit that creates the room - an unreachable server fails go-live with a 503 instead of leaving a LIVE stream nobody can join), and ending a stream closes it without waiting (LiveKit deletes the room, which also disconnects anyone still in it). See docs/features/video-provider.md.

A host can only have **one live stream at a time** - `goLive()` looks up any existing `LIVE` row for that `hostId` and auto-ends it (reason `REPLACED`, including the `stream.ended` event) before creating the new one. Lives whose host app crashed or lost its connection are ended by the heartbeat sweeper within ~2 minutes (docs/features/realtime.md).

Ending a stream does **not** call the realtime gateway directly - it emits `DomainEvents.StreamEnded` and `RealtimeModule` listens for it. Neither module imports the other (see docs/features/events.md and plan §4.1).

**Stage layout** (plan §6.1): `streams.layout` (`FULL` default, `FIT`, `SPLIT`, `FLOATING`, `MINIMAL`) is how the host wants the live composed on every screen. `POST /v1/streams` accepts an optional `layout`; `PATCH /v1/streams/:id/layout` switches it mid-live - host only (`PermissionsService.canEditStreamDetails`), live streams only, and a no-op (no write, no event) when unchanged. A change emits `DomainEvents.StreamLayoutChanged`, which the gateway relays to the room as `stream:layout_changed` `{streamId, layout}`; viewers who join later read it from the join response's `stream.layout`.

**Room bans** (`banFromRoom()`/`unbanFromRoom()`, plan §6.4): the host, or a moderator holding `BAN_USERS` (checked by a private `canUseCapability()` helper - the same shape as `ChatService`'s, host always passes, otherwise fetches the requester's `ModeratorGrant` via `ModeratorsService.findActiveGrant()`), bans a participant with a `RoomBanScope` of `SESSION` (this stream only) or `HOST_PERMANENT` (every future stream from this host). `RoomBansService` (`apps/backend/src/room-bans`) owns the `RoomBan` table and emits `room_ban.created`; `RealtimeGateway.handleRoomBanCreated` evicts the banned user's sockets from that one stream room (`socketsLeave`, for a `SESSION` ban with a concrete `streamId`) and always emits `force_disconnect {hostId, streamId, scope}` to their private `user:{id}` room, so a client currently watching that host can leave immediately instead of waiting to be refused on rejoin. `join()` (both the REST endpoint and `stream:join` on the gateway) calls `RoomBansService.isBanned(hostId, viewerId, streamId)` - true for either a matching `HOST_PERMANENT` row or a `SESSION` row scoped to this exact stream - before minting a token or admitting the socket.

**Viewer list** (`listViewers()`, plan §6.13): 404s unless the stream is currently live (`findLive()`), then reads every viewer's user id from presence (`LivePresenceService.viewerIds()` - an `HKEYS` over the same Redis hash the viewer count is derived from), sorts them for a stable cursor, pages by a plain "last id seen" cursor, and hydrates the page with one `prisma.user.findMany` (reordered to match the paged id list, since Prisma doesn't preserve `in` order).

**Moderator management** (`listModerators()`/`grantModerator()`/`updateModerator()`/`revokeModerator()`, plan §6.9 - see docs/features/moderators.md for the full feature): all four are host-only (`PermissionsService.canManageModerators`, a plain `isHost` check - a moderator can't grant, edit, or revoke another moderator, and can't see the roster either). `grantModerator()` specifically uses `getLiveOrThrow`, not `getOrThrow` - a grant is scoped to the stream it's made for (revised 2026-09-26: originally a persistent per-channel role; changed so it doesn't carry over to the host's future streams), so it only makes sense to create one while that stream is actually running. `updateModerator()`/`revokeModerator()` use the plain `getOrThrow` (no live requirement) since editing or removing an already-inert grant is harmless either way. All four delegate straight to `ModeratorsService`, which owns the `(streamId, userId)`-keyed data itself.

**Post-live summary** (plan §6.13, Phase 7 - `GET /v1/streams/:id/summary`, host only via `canStartOrEndStream`): `{streamId, durationSeconds, peakViewerCount, likeCount, newFollowers}`. Once ended it reads the persisted `peakViewerCount`/`likeCount`; while still live it reads presence (falling back to the columns if Redis blips), so the ended screen never races the end. `newFollowers` counts follows of the host created between `startedAt` and the end - someone who followed and unfollowed again during the live isn't counted. The mute-suite routes also live on `StreamsController` but are documented with their features: room chat mute (docs/features/moderation.md) and the guest mic lock (docs/features/guests.md).

**Recording permission** (client request, 2026-09-30): the app keeps a live out of screen recordings and screenshots for everyone watching it, except the viewers its host allows. `POST /v1/streams/:id/recording-permissions/:userId` (host only, while live; not the host themselves, who always may) allows one viewer, `DELETE` takes it back and `GET /v1/streams/:id/recording-permissions` lists who may. Moderators can't grant it. `RecordingPermissionsService` (`src/recording-permissions`, table `recording_permissions`, one row per live and viewer, so it ends with the live) emits `recording_permission.changed`, which the gateway relays privately as `recording:permission {streamId, allowed}` to that viewer's `user:{id}` room. `join()` returns `canRecord`, and so does every `stream:join` ack, so a reconnect catches up (docs/features/realtime.md).

On the phone (`lib/core/screen_protection.dart`, `ScreenProtection`): the viewer screen asks for protection from the moment it opens and lets go only when `canRecord` says so, following `RoomSynced` and `SelfRecordingAllowed` ("<host> lets you record this live" / "turned off recording for you"). Protection is held per screen and stays on while any live screen wants it, so swiping between lives never leaves a gap. Android sets `FLAG_SECURE` on the window (`gambling_live/screen` channel, `MainActivity.kt`): screen recordings and screenshots of the app come out black, and the live is hidden in the recent-apps view. iOS can't block a recording, so `AppDelegate.swift` reports `UIScreen.isCaptured`: while the screen is being recorded or mirrored, the live is covered ("Recording isn't allowed in this live") and stops coming in (`setPaused`, so no sound is recorded either); iOS screenshots can't be blocked. The host's own go-live screen is never protected. The host sets it from the viewer's profile card "..." menu ("Allow recording" / "Stop allowing recording"). **Limits**: the share page's web player can't stop a browser or another device recording the screen; a camera pointed at the phone can't be stopped by anything.

## Discovery 2.0: For You, search, private and scheduled lives, live pictures (2026-10)

These supersede the ranking and visibility notes above.

**For You ranking** (`listLive()`, `streams/live-audience.ts`): lives are ordered by `liveScore()`, not by viewers alone - audience (`log2(1 + viewers)`, so a huge live doesn't bury every small one), engagement (likes a minute, from Redis), freshness (a boost fading over a live's first 15 minutes, so a new live can find viewers), the viewer's ties to the host (follows +3, friends +1.5 more), their interests (the share of the lives their followed hosts ran in the last 60 days in this live's category) and a paused live sinks (-2). The weights are `RANKING_WEIGHTS`, in one place to tune. Discovery is now always called signed in by the app.

**Search** (`GET /v1/streams?q=`): part of a title, or the host's name or username, case-insensitive; same audience rules and ranking. The app's search screen shows matching lives ("Live now") above people.

**Who can watch** (`streams.visibility`, `StreamVisibility`: `PUBLIC` default, `FOLLOWERS`, `FRIENDS`; migration `20261010110000_stream_visibility`): chosen on the go-live screen ("Who can watch"). One rule, `canWatchLive()`, behind every way in: discovery and search (filtered per viewer), `POST /streams/:id/join` (403 `LIVE_RESTRICTED` with "This live is for the host's friends." - the app shows it as "This live is private"), the share page's player (`POST /watch` - a browser is never let into a restricted live; the share page shows "A private live" and "Open in the app" instead of the title and player), `stream:join` on the gateway, `GET /streams/:id` (a running restricted live is a 404 to anyone else), a profile's LIVE ring (`liveStreamId`), "Send to friends" invites (only friends who may watch), and go-live notifications (a friends' live notifies only followers the host follows back). `StreamsService.canWatch()` also always lets in the host, a guest on stage and a moderator of the live, so a reconnect never locks them out. Discovery cards badge a followers'/friends' live.

**Live pictures** (`streams.thumbnailUrl`, migration `20261010100000_stream_thumbnails`; `StreamThumbnailsService` / `StreamThumbnailsController`): the host's app takes a frame 6 s after going live and then every 60 s (`LiveThumbnails`, `lib/features/live_stream/video/live_thumbnails.dart` - skipped while the camera is off, paused, in the background or reconnecting), shrinks it natively to a ~20 KB JPEG (longest side 480 px - `compressJpeg` in `MainActivity.kt` / `AppDelegate.swift`), uploads it straight to storage (`POST /streams/:id/thumbnail/upload-url`, then `PUT /streams/:id/thumbnail {key}` - host only, while live, keys checked to be this live's, 10 a minute), and the previous file is deleted. The last one is removed with its file when the live ends. Discovery cards show it over the category art (decoded at card size), the live's loading preview shows it dimmed, and a public live's share link uses it as `og:image`.

**Scheduled lives** (`src/scheduled-lives`, tables `scheduled_lives` + `scheduled_live_reminders`, migration `20261011090000_scheduled_lives`): a host announces a live ahead from the go-live screen ("Schedule for later": title, date, time, who can watch; 5 minutes to 30 days ahead, at most 10 coming up). It shows on their profile ("Upcoming lives", with Cancel on one's own) and in their followers' Following tab ("Coming up", the next 7 days), each with **Remind me** for whoever may watch it (`PUT/DELETE /scheduled-lives/:id/reminder`). `ScheduledLiveReminderJob` (every minute, one instance via a Redis lock) sends `SCHEDULED_LIVE_SOON` ("X goes live soon: title") to the reminded about 10 minutes ahead, once. Within an hour either side of its time the go-live screen offers "Go live for <title>" (title, category and audience filled in); going live with `scheduledLiveId` links it, and the `stream.started` fan-out then also notifies the reminded who aren't followers (on a public live). A scheduled live stays on show until an hour past its time. Routes: `POST /scheduled-lives`, `GET /scheduled-lives/mine`, `GET /scheduled-lives/following`, `GET /scheduled-lives/hosts/:hostId`, `DELETE /scheduled-lives/:id`.

**Portrait video**: the apps capture 640×360 and the encoders keep that size, with the picture's rotation sent alongside (WebRTC's video-orientation header on LiveKit; Agora's adaptive orientation encodes 360×640 for a portrait phone) - every receiver turns it upright, which is why device logs show "640×360" for a portrait live. Worth a device check that the web player and both apps show it upright on both vendors.

**Host screen layout** (client feedback, 2026-10): while live, the top left is the host's own picture and name with the LIVE timer under it (`_HostIdentity`), and the top right a red power button that ends the live (with the usual confirmation) - the old top-left X and the bottom stop button are gone; before going live the preview keeps its close X. On both live screens the chat takes at most 22% of the stage's height (`kStageChatHeightFraction`, was 30%), which brings the live's title down, and sits just above the controls (the arrival row under it is the gap).

## No title or game type; the board; camera effects (client request, 2026-10)

### No title or game type

The app no longer asks for a title ("e.g. High-stakes Friday night") or a
game type (the Poker / Slots / … chips), on the go-live screen or as a
filter on the main screen.

- `POST /v1/streams`: `title` and `category` are optional (older apps still send them). A live started from a scheduled live takes that one's title; any other has an empty title.
- Everything that showed a title falls back:
  - **Notifications:** "Abebe is live now", "… invited you to a live".
  - **Share page:** "Abebe's live" (`liveLabel`/`titleSuffix`, `streams/live-title.ts`).
  - **Audit and report labels:** `null`, or "Live by @abebe".
  - **Console:** `liveName` (`lib/live-name.ts`).
- **App:** discovery cards and the swipe preview lead with the host (avatar and name), plus the scheduled title when there is one. The placeholder art is per host (`AppColors.liveGradient(hostId)`), and the stage no longer shows a title panel.
- **Kept:** the `title`/`category` columns, the `category` query filter, and scheduled lives' own title (it says what's coming).

### The board

A short, see-through text the host puts on the stage, for example "Bingo round 3 at 8:30".

- **Who:** the host, or a moderator holding the new `EDIT_BOARD` capability ("Write and move the text on the live"; Full moderator includes it).
- **What they can do:** write it, edit it any time, drag it anywhere, and take it down. Everyone in the live sees each change at once, the web player too.

**Data and API.**
- **Columns:** `streams.boardText` (null: none), and `boardX`, `boardY` (0 to 1, placing it within the stage's free space). Migration `20261016090000_live_board` (adds the columns and `EDIT_BOARD`).
- **`PUT /v1/streams/:id/board {text?, x?, y?}`:** leaving out `text` moves the board that's there.
- **`DELETE /v1/streams/:id/board`:** takes it down (`LiveBoardService`, `src/live-board`).
- **Text rules:** at most 4 lines and 120 characters. Spaces in a line are tidied and blank lines dropped (`cleanBoardText`). Live chat's banned-phrase filter applies (REJECT refuses with `BOARD_BLOCKED`, MASK masks), and so does its link policy (`LINK_NOT_ALLOWED`).
- **Realtime:** event `stream.board_changed` → `stream:board {streamId, board}` to the room. The room state from `stream:join`, `stream:watch` and `stream:host_join` carries `board`, so late joiners and reconnects get it. `POST /streams` and `/join` answers carry it as `boardText`/`boardX`/`boardY`.

**App.**
- **On screen:** `LiveBoardView` on the stage (`LiveStage.board`), above the video and guests and under the controls and chat. It's never hidden with the controls. Its area is the video, clear of the top bar and bottom controls, so dragging can't put it under a button.
- **Look:** see-through black at 28%, with white text and a soft shadow.
- **Editing:** editors drag it (the move is saved on release, shown at once, and put back if refused) and tap it to edit or remove (`showBoardEditor`). `BoardController` keeps it in step.
- **Entry points:** the host has **Text** in the live controls; a moderator with `EDIT_BOARD` has a **Text** button on the right rail.
- **Web player:** `Stage.tsx` draws it the same way (CSS: `left x%` and `translate(-x%)`, Flutter's `Align`).

### Camera effects (beauty and filters)

**Beauty:**
- **Smooth:** an edge-keeping blur, strongest on skin tones.
- **Brighten:** a log curve that lifts shadows and midtones.
- **Rosy:** a warm glow on skin.

One-tap looks: **Off**, **Natural** and **Glow**.

**Filters:** None, Natural, Warm, Cool, Vivid, Soft, Vintage and Mono, each a 3x4 color matrix (`CameraFilter`), with a **Strength** slider.

What's seen in the preview is what viewers get. Settings are kept on the phone (`cameraEffectsProvider`, `shared_preferences`) and used from the first preview frame. A guest's camera on stage wears the phone's saved look too.

**How it's drawn.**
- **LiveKit on Android:** `CameraEffects.kt` adds a processor to flutter_webrtc's `LocalVideoTrack` (its `ExternalVideoFrameProcessing` hook).
  - **Pipeline:** each camera frame (an OES or RGB texture, on WebRTC's camera thread with its EGL context) is drawn through one fragment shader into a pooled `GlTextureFrameBuffer` (4 of them), and goes on as a `TextureBufferImpl`. Nothing is copied to the CPU.
  - **When nothing is on**, frames pass through untouched.
  - **Pool full:** a frame goes out as it came.
  - **GL errors:** the effects turn off for that camera; the live goes on.
  - **New camera:** effects are put on every new camera track (flip, reopen, camera back on) through `onCameraStarted`.
  - **Dependency:** the app compiles against the same WebRTC flutter_webrtc ships, as `compileOnly`. Keep the versions in step when upgrading flutter_webrtc.
- **Agora:** its own `setBeautyEffectOptions` (smooth, brighten, rosy); Agora has no color filters, so the sheet shows Beauty only.
- **iOS:** not yet (`supportsEffects` false on LiveKit/iOS).

**UI:** **Effects** on the go-live preview and in the live controls opens `showEffectsSheet`. It's see-through at the top, so the host watches the change as it happens.

## Hosting restrictions (2026-10)

Staff can pause a host's streaming because of a live
(docs/features/hosting-restrictions.md): `goLive`, raising a hand,
accepting or being sent a stage invite, and scheduling a live are refused
with `403 HOSTING_RESTRICTED`; a running live ends with
`StreamEndReason.HOST_RESTRICTED` and the user leaves any stage
(`StreamsService.handleHostingRestricted`). Watching is never affected.

## How to add to this feature

- **A new room-ban scope**: add the value to the Prisma `RoomBanScope` enum (+ migration) and a branch whichever side of `RoomBansService.ban()`/`isBanned()` needs it - both already switch on `scope`, not a boolean.
- **A new viewer-list sort** (e.g. "guests first", "moderators first"): `listViewers()`'s ordering is a single `.sort()` on the id array from presence - swap the comparator or hydrate extra fields (moderator status, guest status) to sort by before slicing the page.
- **Scheduled streams**: `CreateStreamDto` and `goLive()` currently always set `status: LIVE`; a "go live at a scheduled time" flow would add a `SCHEDULED`-status path instead of changing this one.
- **New list filters**: extend `ListStreamsQueryDto` and the `where` clause in `listLive()`. Past a few hundred concurrent lives, move the ranking into Redis (a sorted set per category updated with the counts) instead of ranking in memory.
- **A new stage layout**: add the value to the Prisma `StreamLayout` enum (+ migration), then to the mobile `StageLayout` enum (`wireValue` must match) and a case in `LiveStage`'s geometry and the picker thumbnail. Older app versions map unknown values to Full screen, so adding one is safe.

## How to modify this feature

Who can end a stream is gated through `PermissionsService.canStartOrEndStream` (§4.1) - to let moderators end a stream too (they currently can't, by design, see plan §6.9), change that one method, not this controller/service. Who can ban a participant is a separate, narrower check (`canUseCapability()` against `ModeratorCapability.BAN_USERS`) - it doesn't reuse `canStartOrEndStream` since a moderator can be allowed to do one without the other.

## How to remove this feature

Remove `StreamsModule` from `app.module.ts`. `RealtimeModule` only reacts to the `stream.ended`/`stream.layout_changed`/`room_ban.created` events (no direct import), so it degrades gracefully (nothing to clean up there) - but `apps/mobile`'s discovery/go-live/viewer screens call these endpoints directly and would need their own removal. Removing just the ban/viewer-list/moderator-management additions on their own: delete `banFromRoom`/`unbanFromRoom`/`listViewers`/`listModerators`/`grantModerator`/`updateModerator`/`revokeModerator`/`canUseCapability` from `StreamsService`, the matching routes from `StreamsController`, and the `ModeratorsModule`/`RoomBansModule` imports from `StreamsModule` - the room-ban check in `join()` and `stream:join` would need to go too, or every join would 500 calling a service that's no longer injected.

## Tests

`streams.service.spec.ts` covers: go-live on the active provider (stored vendor + channel name, publisher token, channel opened before the row, no row when the media server is down), audience token from the vendor the live started on plus whether the viewer already follows the host (`isFollowingHost`) and this viewer's own moderator capabilities for THIS stream (`selfCapabilities`, keyed by `streamId` - see the bug note below), rejecting a join to a non-live stream or one the viewer is room-banned from, host-only enforcement on end, that `end()` emits `stream.ended` with its reason, persists the peak and closes the channel (and still ends when that fails), ending only once when two paths race, auto-ending a host's previous live as `REPLACED`, going live counting as the first heartbeat (and still working when Redis blips), discovery ranking/pagination/category filter (newest first when counts are unavailable), blocked-host exclusion and its combination with `feed=following` on the same `hostId` filter, `GET /streams/:id` (live, ended, unknown), the sweeper's `endAbandonedLives()` (and its grace window), `getVideoConfig()`, layouts (go-live persists the picked layout; the host can switch it mid-live and it's broadcast; unchanged → no write/event; non-host → 403; ended stream → 404), room bans (host or a moderator with `BAN_USERS` can ban/unban; refused without the capability), moderator management (grant requires the stream to be live and the host; a moderator can't grant another moderator; edit/revoke/list are all host-only), and the paginated viewer list (hydrated and reordered from presence; 404 when not live). `realtime.gateway.spec.ts` covers the `stream:join` ban check and `handleRoomBanCreated` (evicts the specific room for a session ban, notifies either way, skips eviction with no room for a permanent ban). `room-bans.service.spec.ts` covers the ban/unban/isBanned store directly.

**A real bug caught while wiring the mobile side, not by a failing test at first**: `ModeratorsService.findActiveGrant()`'s first parameter changed from `hostId` to `streamId` when grants were rescoped per-stream (2026-09-26), but `StreamsService.join()`'s own call site - `this.moderators.findActiveGrant(stream.hostId, viewerId)` - was missed in that same edit, since TypeScript can't catch a same-shape parameter reordering (both are plain `string`s) and the call site's own test asserted the OLD argument, so it didn't fail either until the assertion was corrected to match the intended behavior. Caught by re-grepping every `findActiveGrant(` call site across the codebase after the signature change, on the theory that a renamed/reordered parameter is exactly the kind of change `tsc` can't verify for you. Fixed to `this.moderators.findActiveGrant(streamId, viewerId)`. Also exercised live end-to-end via `apps/backend/scripts/smoke-test-realtime.js` (on both vendors).

## Mobile (`apps/mobile/lib/features/live_stream`, `discovery`)

Every screen is built from the shared design system in `lib/core/theme` (`AppColors`, `AppSpacing`, `AppRadius`, `AppTheme`) and `lib/core/widgets` (`PrimaryButton`, `AppTextField`, `LiveBadge`, `ViewerCountBadge`, `WeakConnectionBadge`, `GradientScrim`, `EmptyState`, `MelaLogo`) - **reuse these instead of hardcoding colors/paddings/one-off buttons** when building Phase 2+ screens (chat, guests, moderation), or the app will visually drift apart screen by screen.

`GoLiveScreen` (publisher) and `ViewerScreen` (audience) never call a vendor SDK directly: they drive a `HostVideoSession` / `ViewerVideoSession` (`video/`), implemented for Agora (`agora_rtc_engine`) and LiveKit (`livekit_client`) - see docs/features/video-provider.md for the LiveKit side. Two facts about the Agora session worth knowing before touching it, discovered by actually checking the installed package source (v6.6.4) rather than assuming:
- `setLocalPublishFallbackOption` **does not exist** in this SDK version - only `setRemoteSubscribeFallbackOption(StreamFallbackOptions)` (viewer/audience side) and `enableDualStreamMode(enabled: true)` (publisher side, so viewers can auto-pick a quality) are real APIs. Don't re-add a local-publish fallback call without re-checking the installed version first.
- `DiscoveryScreen` deliberately renders a static initial-letter avatar per stream, not a video/thumbnail preview - see plan §7 (no autoplay).

**Discovery** (`lib/features/discovery`): a **For You | Following** tab switcher (`DiscoveryRepository.listLive(feed:)`) sits where the screen's static headline used to be - Following calls `feed=following` and shows a distinct "find people to follow" empty state; see docs/features/social.md for the full social feature. The grid itself keeps the server's ranking - most-watched first - with the LIVE badge and a `ViewerCountBadge` ("1.2K") on every card, and one screen-reader label per card ("Live: title, by host, category, N people watching"). Category chips filter on the server; the next page (`DiscoveryRepository.pageSize`, 20) loads when the grid is scrolled within 600 px of its end, skipping lives already shown (rankings move between pages). While the first page loads it shows a pulsing skeleton grid (still with reduce-motion). It reloads on pull-to-refresh, on the way back from a live, and when the app returns to the foreground after 30 s or more. A failed reload keeps the list on screen - only pull-to-refresh says so, in a snackbar - and only an empty screen shows the error state.

**Swiping between lives** (client feedback, 2026-09-29 - `features/live_stream/feed/`): `/live/:id` opens a `LiveFeedScreen`, a vertical feed - swipe up for the next live, down for the one before, TikTok-style. Discovery passes what it showed (`LiveFeedSeed` as the route's `extra`: the lives on screen, the category and For You/Following filter, the last page), and `LiveFeed` pages on with the same filter as the viewer nears the end (`prefetchDistance` 3), never listing a live twice. Opened from a link or a notification (no seed), the feed is that live, then the most-watched after it. `LiveFeedPager` builds only the page a swipe has **settled** on (`ScrollEndNotification`) as a live `ViewerScreen`; every other page is a `LivePreview` (the host's picture, name and title over the category colors - also what a `ViewerScreen` shows while it loads, so the hand-off is seamless). So there's only ever one video connection and one room, a swipe that springs back connects nothing, and leaving a live (its screen disposed) frees its connection before the next one starts. It holds still while the viewer is on stage (`ViewerScreen.onStageChanged` - leaving the stage takes a confirmation) or typing. Agora's engine is one per app (`createAgoraRtcEngine()` hands out the same instance until it's released), so a quick swipe could start the next live's session while the last one's is still being torn down: `MediaEngineGate` (`video/media_engine_gate.dart`) serializes that - sessions create their engine only once every release in flight has finished. Swiping doesn't change the route, so `watchingLiveProvider` (`feed/watching_live.dart`) says which live is on screen - the in-app notification banner reads it to stay quiet about that live.

**No other live while broadcasting** (client feedback, 2026-09-29): a host can't open - let alone swipe through - other lives until they end their own, and a guest on stage can't until they leave it. `broadcastingProvider` (`broadcasting.dart`) holds the live this device broadcasts in and how (`BroadcastRole.host` from `GoLiveScreen` once live until it ends; `BroadcastRole.guest` from `LiveFeedScreen` while on stage), and the router's `onEnter` (`guardLives` in `app/router.dart`) blocks every navigation to `/live/:id` meanwhile - a notification's View, the inbox, a push tap, a share link, a profile's LIVE ring - staying where it is with a snack bar ("You're live. End your live to watch other lives."), silently for the live already being broadcast. Back was already held on both screens; this closes the routes pushed on top, which would also have started a second media session on Agora's one engine. It returns `Block.stop()` (not `Block.then`, whose kept redirect history would reach go_router's limit after a few taps) and lets signing out through. The notification banner drops View for lives meanwhile. While hosting, the host's own profile and settings stay shut the same way (`/profile`, `/profile/edit`, `/profile/friends`, `/settings`, `/settings/privacy` - "You're live. End your live to open your profile.", client feedback, 2026-10), and tapping their own name in the live opens no card.

**Pause** (docs/features/realtime.md): while live, the host's Pause button (next to End stream) turns their camera and microphone off, shows them a paused screen (camera flip and zoom are off meanwhile), and puts every viewer on "Live paused"; the host's LIVE badge turns into an amber PAUSED one (and so does the discovery card), with the timer still running. Resume turns both back on. A viewer's own pause button (top right) stops their video and audio - saving data, letting the phone sleep - and a tap on the paused screen resumes at the live's current moment.

**Live timer and the ended screen**: the running time is **the host's alone** (client feedback, 2026-09-28): the host's screen shows `LiveBadge(clock:)` ("LIVE 12:34", ticking once a second in its own widget, so the screen around it doesn't rebuild); viewers and guests have no LIVE badge at all (client feedback, 2026-09-29 - a live they're watching needs no label; a paused host shows as the full "Live paused" notice). Both show the viewer count. When a live ends - the host ended it, the sweeper did, or it was already over when the card was tapped (the join 404s) - viewers see `LiveEndedView` (host, why it ended, an optional Follow CTA when the host is known, "Watch other lives" - no duration: `LiveEndedView` shows it to the host only); a host whose live the server ended sees its host variant. Where the reason isn't known locally, `GET /streams/:id` provides it. The viewer screen's top bar also carries a host pill (avatar, name, a compact Follow button - tap it for the host's profile card) next to the status badges - see docs/features/social.md. Being room-banned (plan §6.4) is `LiveEndReason.banned` - a client-only reason (never a real `endedReason` value, `fromWire` never matches it) synthesized the moment `LiveRoom` gets a `SelfBanned` event, reusing the same ended-screen machinery with its own headline/explanation and no Follow CTA.

**Viewer list** (tap the viewer count, `showViewerListSheet(context, members:)` in `features/moderation/presentation/viewer_list_sheet.dart`): a cursor-paginated sheet of who's watching (`ModerationRepository.listViewers`); moderators carry the MOD badge. Tapping a row opens their profile card, whose "..." menu is the same role-based person menu as anywhere else in the live (docs/features/moderators.md) - no separate per-row menu (client feedback, 2026-09-29). Whoever holds `MUTE_CHAT` sees under each muted row until when; a ban from the card drops the row, and a chat mute or unmute re-reads the mutes (`liveMemberActions`' `onDone`).

**Host post-live summary** (plan §6.13, Phase 7): after End (and after a server-side end) the host lands on `LiveEndedView`'s host variant with a 2×2 of duration, peak viewers, likes and new followers (`LiveStreamRepository.summary`, `LiveSummary`); the places are held while it loads, and without it (offline) the phone's own duration still shows. The view scrolls when it must (small phone, large text). A "Mic off" pill on the host's own status row is a reminder while their mic is off.

**Data Saver** (plan §7, Phase 7 - `features/settings/data_saver.dart`): one device-wide setting, in Settings (`SettingsScreen`, from the profile) and in the sheet the viewer's weak-connection badge opens (`data_saver_sheet.dart`, both through `DataSaverOptions`). Three modes (client feedback, 2026-10 - lives used too much data): **Automatic** (the default) - on while the phone is online through mobile data only (`onMobileDataProvider`, `connectivity_plus`: mobile without Wi-Fi or ethernet), off on Wi-Fi, following the network as it changes mid-live; **Always on**; **Off**. Someone who had switched the old on/off toggle keeps that choice (`data_saver` true/false becomes On/Off; the mode is stored as `data_saver_mode`). Read before the first frame (`readSavedDataSaverMode()` in `main.dart`, like the session) so a live never starts at the wrong quality, and `dataSaverProvider` (what it is right now) is applied live to whichever connection is running via `RemoteVideoReceiver.setDataSaver` - viewers, guests on stage, and the host's own view of guests. Agora puts every remote on the low simulcast stream (`_lowStream`, 320×180); LiveKit sets `VideoQuality.LOW` on each subscribed video track - the SDK then asks the server for the lower of that and what adaptive stream wants (checked in livekit_client 2.13.0's `resolveVideoSettings`), so a good connection can't upgrade it. With dynacast, a host whose viewers all save data sends only the low layer. Audio is untouched.

**No video nobody can see** (client feedback, 2026-10): `RemoteVideoReceiver.setVideoVisible(false)` stops receiving every remote video - the sound plays on - while the app is in the background (`AppLifecycleListener` `onHide`/`onShow`) or another full-screen page covers the live (`TickerMode.valuesOf(context).enabled` turns false for a covered route; a bottom sheet doesn't cover it). Both live screens call it, and each new connection (rejoining, going on stage) starts in the current state. LiveKit's adaptive stream doesn't cover this: it only checks that a view has a size, which a backgrounded or covered view keeps. LiveKit `disable()`s each video publication (and ones subscribed meanwhile), `enable()`s them back; a pause it caused isn't shown as a weak connection. Agora `muteAllRemoteVideoStreams`, combined with the viewer's own Pause.

**0.5× ultra-wide lens** (Phase 7): `HostVideoSession.ultraWideZoom()`/`setUltraWide()`/`isUltraWide`; `cameraZoomStops(ultraWideZoom:)` leads the stops with how far out the camera's wider lens goes (one decimal, at most 0.9x - 0.5x on most back cameras), and tapping it switches lens rather than zooming (pinching crosses between the wide and main lenses; the physical switch can briefly interrupt video). Agora: `queryCameraFocalLengthCapability()` lists the rear one (0.5x) and `setCameraCapturerConfiguration(cameraFocalLengthType: ultraWide)` switches (an error hides the stop for the session - the SDK can't confirm more than that). LiveKit: the app's own native channel gives a camera id to open, and the opened track's `deviceId` confirms it; flutter_webrtc falling back to another camera marks it refused for that side. Android (`CameraZoom.widerCamera()`; front too since client feedback, 2026-10 - a phone whose own camera app has a front 0.5x): another colour camera facing the same way as the one in use whose view is clearly wider - zoom = this camera's view width / that one's, under 0.9, each from camera2's shortest focal length and the active part of the sensor; depth and monochrome helper cameras are skipped. iOS (`CameraZoom.ultraWideCameraId()`): `builtInUltraWideCamera`, back only, 0.5x. Flipping or reopening the camera returns to the main lens. A phone's own camera app can use lenses it doesn't list to other apps, so a 0.5x there doesn't guarantee one here - `adb shell dumpsys media.camera` shows what is listed.

**0.5× by zooming out** (client feedback, 2026-10 - phones that don't list their ultra-wide lens on its own showed no 0.5x): on Android 11+ a camera that's one logical camera over several lenses reports a `CONTROL_ZOOM_RATIO_RANGE` below 1, and a zoom ratio under 1 hands over to its ultra-wide by itself. `HostVideoSession.minZoom()` says how far the camera in use goes (LiveKit: `CameraZoom.minZoom`; Agora and iOS: 1), and `setZoom` takes anything from it to `maxZoom()`. flutter_webrtc only zooms in, by cropping, so below 1 LiveKit calls `CameraZoom.setZoomRatio`: `MainActivity.kt` reaches flutter_webrtc's running Camera2 session by field name - the way its own `CameraUtils.setZoom` does (its keep rules hold those classes in release builds) - and sets `CONTROL_ZOOM_RATIO` on the same repeating request; anything missing returns false and the zoom stays. The stops then lead with that minimum, rounded up to one decimal (0.5x, 0.6x; `cameraZoomStops(minZoom:)`), pinch runs from it to the maximum, and the separate-lens switch above is only offered where the camera can't zoom out itself. Verify on a device: the 0.5x stop on the back camera, pinching through 1x, and flipping back to the front (which starts at 1x again).

`GoLiveScreen` starts a **full-screen local camera preview immediately** on open (via `GET /streams/config`, which says which vendor's camera engine to open - no stream/token created yet), not only after tapping "Start broadcasting" - the session/preview created here is reused as-is for `publish()` once the host actually goes live, rather than recreated (unless the server switched vendors in between). The same screen also has a camera-switch button (`HostVideoSession.switchCamera()`) and zoom: pinch (`onScaleUpdate` -> `setZoom()`), plus camera-app-style **zoom stops** (`widgets/zoom_stops_bar.dart`) - 1x, 2x, 4x, 8x doubling up to the camera's reported maximum, plus that maximum when it's well past the last doubling (`zoomStopsFor`); the active stop shows the live value while pinching ("2.9x"), and a tap glides there in 250 ms (an `AnimationController`, one zoom call per frame; a pinch or camera flip stops it). **Zoom capability must be read only once the camera is capturing**: on Agora, `isCameraZoomSupported()` returned `false` on the device when called right after `startPreview()` (before the camera had even opened), silently disabling zoom. The SDK docs require `onLocalVideoStateChanged` to report `localVideoStreamStateCapturing` first, and each camera has its own range - so every session reports each capture start (`onCameraStarted`: initial preview and after each flip) and the screen re-reads `maxZoom()` then, with a re-check at pinch start as a fallback; a flip resets zoom to 1x. Verified on the SM A566B: both cameras report 8.0, and tapped stops land exactly on 1/2/4/8. If you need the preview config elsewhere, reuse `LiveStreamRepository.getVideoConfig()` rather than duplicating the fetch.

**Both live screens compose through `widgets/live_stage.dart` (`LiveStage`)** - the video plus every overlay, arranged by the host's `StageLayout` (`stage_layout.dart`). The "video only fills the top of the screen" bug was a layout bug, not a render-mode one: a `Scaffold` body gets *loose* constraints, and the old screens' `Stack` had one non-positioned child - the top-bar `SafeArea` row - so the Stack sized itself to that row (status bar 36 + row 64 + nav-bar inset 48 = 148dp) and `Positioned.fill` video filled only that band. (The explicit `renderModeHidden` added earlier was a no-op: it only affects how video fills the view it's given.) `LiveStage` wraps everything in `SizedBox.expand` and positions every child, and `test/live_stage_test.dart` pins the geometry on a 1080×2400 @2.625 phone screen. When editing it:
- **Never let the video's element be re-created on a layout switch** - it's a native platform view (on Android an `AndroidView` texture), and re-creating it flashes black and re-attaches the stream. The video sits under a `GlobalKey`, in one `AnimatedPositioned.fromRect` whose rect is the only thing that changes, inside `_VideoFrame`, which builds the same widget types in every layout; other Stack children carry `ValueKey`s so adding/removing one doesn't shift the rest. A widget test asserts one `initState` across all layouts.
- Changing only `VideoCanvas.renderMode` (Fill ↔ Fit) is cheap: the SDK re-runs `setupVideoView` on the *same* native view when the canvas differs (`isSame` in the SDK's `video_view_controller_impl.dart`).
- Host screens use `Scaffold(resizeToAvoidBottomInset: false)`; `LiveStage` lifts only `bottomPanel` by `MediaQuery.viewInsetsOf(context).bottom`.
- Floating: one finger drags (`onScaleUpdate` with `pointerCount == 1` - pan and scale recognizers can't coexist), two fingers still pinch-zoom on the host; release snaps to the nearest corner (with a little fling projection); `onScaleEnd` ignores pointer-count changes mid-gesture (`pointerCount > 0`). The window stays between the top bar and the measured bottom panel (`_MeasureSize`) and shrinks when that space is short (keyboard up).
- **Controls hide only when nobody touches the screen** (client feedback, 2026-10 - the old sideways swipe that cleared a viewer's screen fired by accident and left no way back, and Minimal's controls could stay gone): a viewer's controls hide after `kStageIdleHide` (1 min) without a touch on Full and Fit (`idleHideAfter`; the host's stay up); Minimal hides after `kStageOverlayAutoHide` (5 s) for everyone; Split and Floating never hide (their video isn't under the controls). Any touch anywhere (a `Listener` around the whole stage) restarts the clock, and on a clean screen brings everything back in place - and does only that: it doesn't like, and doesn't press a button that sat under the finger (the controls ignore touches while hidden). Nothing hides while someone is typing, while a sheet or page is over the live (`ModalRoute.isCurrentOf`), or for a screen reader (`accessibleNavigation`); `keepOverlaysVisible` keeps them up while the host fills in the setup form or is paused.
- **Taps on the video** reach `onVideoTap` in stage coordinates (the viewer likes with them). The top/bottom shading is `IgnorePointer`, so it doesn't swallow them. While a text field has focus, a tap only puts the keyboard away. In Floating the window keeps its double-tap to resize - a single-tap there would have to wait out every double-tap - so taps on the backdrop around it count instead.
- The rail fades out (and ignores touches) while the keyboard is up: it follows the lifted panel and would land on the guests and the chat.

The host picks a layout from the top-bar button (`widgets/stage_layout_sheet.dart`, with a thumbnail per layout), before or during the live. It's applied instantly on the host's screen; once live it's `PATCH`ed and rolled back with a snackbar if the server refuses, so the host never sees a layout their viewers don't. Every live starts on Full screen, whatever the last one used (client feedback, 2026-10 - it used to be remembered). `ViewerScreen` takes the layout from the join response and follows `stream:layout_changed`; after a reconnect, the room's resync (docs/features/realtime.md) catches up a change made during the drop.

Android's `minSdk` is pinned to at least 24 in `android/app/build.gradle.kts` (Agora requirement), `compileSdk` is forced to 36 for **every** Gradle subproject (including plugins) via a `subprojects{}` block in the root `android/build.gradle.kts` (`agora_rtc_engine` ships its own Android module still pinned to compileSdk 31 - overriding only the app module's compileSdk does not fix this; that override must also be registered *before* the template's existing `evaluationDependsOn(":app")` block or Gradle throws), and camera/microphone permissions are declared in `AndroidManifest.xml` / iOS `Info.plist`.

**Validated on a real device** (Samsung SM A566B via `flutter run`) - built, installed, and ran successfully after the two fixes above plus removing `google_fonts` (see below).

**Current video quality behavior**: Agora uses SDK-selected standard bitrate at 640×360/15 fps and a 320×180/15 fps/200 kbps low stream; LiveKit caps its main layer at 400 kbps and publishes a 320×180/10 fps/100 kbps lower simulcast layer. LiveKit explicitly prefers maintaining camera frame rate when bandwidth falls, allowing the SDK to lower resolution. Mobile and web clients report local connection quality; Agora's periodic degradation uses hysteresis, while severe quality loss, reconnecting, Agora audio-only fallback, and LiveKit pausing the host feed show the warning immediately. These settings reduce avoidable load, but no client configuration can guarantee smooth video when device capture, uplink, viewer downlink, or LiveKit server capacity is the bottleneck.

**Current camera zoom behavior**: both cameras zoom (front up to 4x, back up to 10x - docs/features/video-provider.md), a tap to focus keeps the zoom, and a restarted camera gets its zoom back. Zoom stops double from 1x (1x, 2x, 4x, 8x) and add the camera's own maximum only when it's at least 1.5 times the last one. Pinch updates are serialized, coalesced, and limited to 30 camera writes per second; when zooming below 1x requires a separate wide camera, pinching crosses to that lens and back at 1x. The host can use the active front/rear camera's supported range within 0.1×–10×. Many phones cannot zoom below 1× unless they expose a logical multi-lens camera or a wider lens; digital zoom can reduce detail, and switching physical lenses can briefly interrupt video.

Deliberately **not** using `google_fonts`: it fetches font files over the network the first time each one is used, and that fetch failing (as it did on a real device with a flaky connection) throws an uncaught exception that crashes the app - directly contradicting the low-bandwidth/offline-resilience requirement in plan §7. `AppTheme.dark` uses the platform's bundled system font instead. If a custom webfont is wanted later, bundle the actual `.ttf` files as Flutter assets (declared in `pubspec.yaml`'s `flutter: fonts:`) rather than using `google_fonts`'s dynamic fetch - and set `GoogleFonts.config.allowRuntimeFetching = false` too if the package is ever reintroduced, though that alone is not sufficient (it still throws if the font isn't bundled, just with a different message).
